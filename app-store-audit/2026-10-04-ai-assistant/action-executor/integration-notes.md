# Native action executor handoff

The five owned production/test/configuration paths are ready for root integration and a new candidate freeze. No compilation, tests, permission request, notification scheduling, calendar access, account access or device runtime occurred in this implementation pass. The exact hashes and 15 prepared test names are in `implementation-receipt.json`.

`AdultActionExecutor.requestPermission(for:preferences:)` checks the chosen native service before Settings persists its automatic-action opt-in. It does not create an item and does not require that opt-in to be already enabled. The injected system exposes notification authorization, calendar authorization and chosen Reminders-list authorization separately from writes.

The root controller must save `AdultAssistantLibrary.beginExecution` before calling `execute`. The executor accepts that durable `.running` snapshot; it rejects pending, completed, unresolved and receipt-bearing snapshots. A successful call returns the actual external identifier for `finishExecution`. If the native write succeeds but saving the library receipt fails, preserve `.running`/`.needsReview`; do not replace it with a known-no-effect failure. Unknown write errors and missing system receipts expose `uncertainOutcome = true`. Permission, validation and budget failures that occur before writing are safe to record as known-no-effect failures. The library prevents re-execution of completed actions and recovery of interrupted writes without explicit review. The executor never reads an existing event to invent a successful outcome.

App notifications use `AdultAssistant.<action UUID>` and include `assistantActionID` in their tap payload. The root owns the single notification delegate and action lookup. Notification writes now use the root-owned `AdultNotificationBudget.add`, preserving its shared cap of 60 including reservations. Guide reconciliation remains root-owned. The executor's injected check counts every pending request, including `AdultGuide` requests, and replacement of the same notification ID does not consume another slot.

Recurring app reminders use the actual daily, weekly or monthly native trigger. Their planned start must be the next matching local-calendar occurrence because a repeating notification trigger has no separate distant start boundary. A later initial date is rejected rather than firing early. Monthly dates 29–31 skip months without that date. Calendar and Apple Reminders recurrence use EventKit rules anchored to the supplied scheduled date.

EventKit construction is lazy. The default calendar path requests write-only event access and writes to the system's default calendar. A selected calendar identifier requires already-full event access; under write-only access the adapter rejects it before reading the calendar list. The adapter does not request full event access automatically, read events, resolve conflicts, update or overwrite previously completed events. Apple Reminders export requires the explicit list identifier and full Reminders access. All native records include the stable action UUID in their notes for manual review.

Both Info files add only the three modern EventKit usage strings. The Mac entitlement adds only sandbox Calendar access. Their inverse text diff matches the saved pre-edit configuration bytes. Existing version, encryption, catalog URL and other settings remain byte-for-byte intact apart from those authorized additions.

The 15 tests inject a value-only mock system. They cover opt-in without creation, permission denial, durable-running requirements, completed/review rejection, disabled automation and invalid dates, stable notification IDs, the shared limit, recurrence start and calendar patterns, genuine mocked service receipts, uncertain writes, dates expiring while permission waits and cancellation before execution. They do not construct the native adapter, access a user's calendar or request OS permission. They are prepared evidence, not passing-test claims.

Next validation is a root-owned matching iOS/macOS compile, then the offline injected tests in the approved private host. Any real notification delivery/tap validation needs its separate allocated private runtime. Calendar/Reminders system behavior has not been exercised against live user data.
